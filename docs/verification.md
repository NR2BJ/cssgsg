# 검증 현황

사용자는 세 배열(참신세벌식, Graphite, 新月配列)을 써본 적이 없다. 그래서 동작이 맞는지 손으로 확인할 수 없다.
게다가 이 입력기로 처음 배우게 되므로, 동작이 틀리면 잘못된 손버릇이 그대로 몸에 밴다.
그래서 **서로 독립된 출처끼리 대조**해서 검증한다. 엔진이 읽는 데이터와 다른 파일, 다른 구현을 정답으로 삼는다.

## 정답의 우선순위

1. 원작자 자료: 참신세벌식은 공빈의 확정안 글과 날개셋 `.ist`, 新月은 공식 표 두 가지, Graphite는 공식 keylayout.
2. 원작자 구현: 날개셋. **아직 대조하지 못했다**(윈도우 전용).
3. 다른 구현: 오이, 타닥. 원작자 규칙과 다르면 원작자를 따른다.

## 아직 검증하지 못한 것

- **날개셋(원작자 구현)과 대조:** 윈도우 PC에 날개셋과 `.ist`를 올리고, 자동 타자(AutoHotkey)로 키열을 쳐서 결과를 읽는 하네스를 만든다(Phase 3, 원하면 더 일찍).
  애매한 칸은 두 가지다: 겹받침 뒤 왼손 키, 받침 낱자 뒤의 키. 둘 다 실제 한국어 타자에서는 거의 나오지 않는다.
- **맥 입력기 셸(Phase 2):** 키 변환 계층(NSEvent → 코어)은 위 스모크 테스트로 검증했다. 남은 것은 IMKit 컨트롤러가 실제 앱과 주고받는 부분이다.
  앱 호환(Firefox, Codex, Discord, KakaoTalk, VS Code), 조합 중 글자 표시, ⌘+키 재전송, Chromium Shift+Enter, 후보창, 비밀번호 칸.
  다음 두 가지로 확인한다.
  - 테스트 앱에 합성 키 이벤트를 쳐 넣는 자동 E2E.
  - 사람이 볼 체크리스트. 배열을 몰라도 확인할 수 있게 "이 키를 누르면 이게 보여야 한다" 꼴로 만든다.
- **Mozc 변환:** 엔진을 붙인 뒤 품질과 지연을 잰다.
- **받은 Mozc 엔진을 실제 입력기에서 쓰는 것(0.6.0):** 시험 프로그램은 입력기와 같은 코드로 받은 엔진을 읽지만, IMKit이 띄운 입력기
  프로세스에서 읽는 것은 엔진 워크플로가 앱에 든 것보다 새 Mozc를 낸 뒤에야 처음 본다(지금 upstream 최신 = 앱에 든 a069a88).
  설정 앱 일본어 → 변환 엔진의 "내려받은 엔진" 표시와 개발자 기록(`[Mozc] ready … source=downloaded`)으로 확인한다.
- **설정 앱을 실제로 쓰는 것:** 입력기가 떠 있는 진짜 창에서 녹화하기, 입력기 프로세스의 Mozc가 사용자 사전을 다시 읽는 것, 후보 글자 크기 바로 적용, 화면 언어를 바꾼 메뉴 막대 메뉴. [확인 목록](mac-checklist.md) 23~41번으로 본다(0.5.0 사용자 확인: 28번 Control+Return이 Discord에서 전송됨 → 0.5.1에서 고침).
- **모드 HUD 자리:** 사용자가 "살짝 어긋난다"고 했다(0.5.0). 이 컴퓨터에서는 AX가 늘 실패하고 `attributesAtCaret`(폭 1의 커서 자리)을 쓴다. 0.5.1부터 HUD 자리를 기록하므로, 앱과 어긋난 쪽을 받으면 기록과 맞춰 본다. 0.6.4부터 줄 맨 앞(0번 글자)과 앱 창 밖 자리는 버리고 마우스 옆에 띄운다(버린 것은 `[HUD] caret outside the app's windows`로 남는다).
- **설정 앱에서 업데이트 설치:** 0.5.0보다 새 릴리스가 나와야 처음 해 볼 수 있다(0.4.0 → 0.5.0은 입력기 메뉴의 옛 업데이트로 간다). 설치 셸의 동작은 위 스모크 테스트가 가짜 osascript·open으로 확인한다.

## 문제를 찾았을 때

개발자 모드에서 키 기록을 남긴다. 기록에는 키 코드, 수식키, 시각만 들어가고 글자 내용은 들어가지 않는다.
그 기록을 코어에 그대로 재생하면 같은 상황을 재현할 수 있고, 재현되면 테스트로 굳힌다.
